# Factorio RLVR benchmark 0.2 development catalog

The development manifest is generated by `fle.envd.benchmark`. Version
`0.2.0-dev` adds a short-horizon API competence benchmark beneath the existing
industrial curriculum. It currently contains 60 engine-grounded tasks across
six suites:

| Suite | Scope |
|---|---|
| `lab_throughput_v1` | 30 automatic production targets from mining through late-game science |
| `milestones_v1` | Research completion and rocket launch |
| `progression_v1` | Persistent early-game industrial progression |
| `robustness_v1` | Productive survival and action-restricted automation |
| `efficiency_v1` | Throughput under pollution and raw-resource budgets |
| `api_microtasks_v1` | 24 early- through late-game API and compact integration tasks |

Twenty-one microtasks have been manually solved against the pinned Factorio
2.0.73 engine and are marked `ready`. Three integrated tasks—belt routing,
offshore-pump connection, and powered assembly—remain
`calibration_required`. Existing longer tasks retain their own readiness
status.

Microtask success can be based on character inventory, entity count, status,
configured recipe, entity inventory, or exact position. Required and forbidden
FLE calls are checked from audited tool hooks. A task does not pass merely
because the model prints a claim or places the right prototype in a broken
state.

The later-game slice covers chemical-plant and refinery recipes, uranium
processing, modules, pumpjacks, roboports, rocket-silo placement, automatic
circuits/red science/steel, and a compact Logistics research milestone.

The catalog still does not claim train, circuit-network, logistic-robot,
combat, or repair coverage. These become benchmark suites only after adding
the corresponding engine predicates and procedural state-corruption operators.

## Programmatic discovery

```python
from fle.envd import benchmark_catalog, benchmark_summary

print(benchmark_summary())
for task in benchmark_catalog():
    print(task.task_id, task.suite, task.tier, task.status)
```

Every entry includes:

- a reproducible `FactorioTaskSpec`;
- suite, tier, horizon, mechanic tags, and development split;
- readiness status and calibration notes;
- a primary metric;
- verifier and provisioning metadata.

## Verifiers v1 selection

A complete ready suite can be selected without copying task IDs:

```toml
[orchestrator.train.env.taskset]
benchmark_suites = ["robustness_v1"]
benchmark_statuses = ["ready"]
```

Multiple suites may be combined. Explicit `task_specs`, `builtin_task_ids`, and
benchmark suite selections are de-duplicated by task ID.

For the microtask suite:

```toml
benchmark_suites = ["api_microtasks_v1"]
benchmark_statuses = ["ready"]
```

## Inference-only baseline runs

`fle-benchmark` evaluates any OpenAI-compatible model server through the same
`factorio-envd` contract used by Verifiers:

```bash
fle-benchmark \
  --model-base-url http://127.0.0.1:18080/v1 \
  --envd-url http://127.0.0.1:8172 \
  --suite api_microtasks_v1 \
  --status ready \
  --attempts 3 \
  --output benchmark/results/my-model.json
```

The command writes:

- a provider-neutral run record;
- one full trajectory per task attempt;
- an aggregate summary with success rate, invalid-intervention rate,
  per-task scores, and per-mechanic scores.

Validate a proposed result before publishing:

```bash
fle-benchmark-results validate benchmark/results/my-model.json
fle-benchmark-results summary benchmark/results/my-model.json
```

Validation rejects unknown tasks, mismatched benchmark versions, and task
fingerprints that do not match the checked-out catalog.

The runner also records the model-facing action-reference identifier and its
SHA-256. This separates API onboarding conditions: changing callable
signatures, examples, or namespace guidance can change pass rates even when
the underlying task and verifier are unchanged.

### Tool-error retries

Evaluation can grant a bounded recovery allowance:

```bash
fle-benchmark \
  --tool-error-retries 2 \
  --output benchmark/results/model-retry-assisted.json
```

An engine-rejected program consumes one retry credit and remains in the trace
with its invalid-action penalty, but does not consume the ordinary intervention
budget. The model receives another turn; the harness never rewrites or replays
the program. Because executed statements can persist before a later statement
fails, this is not a transactional rollback.

Strict (`0` retries) and assisted runs are different benchmark conditions and
must be published separately.

## Release requirements

Before changing the version from development to a frozen benchmark:

1. Collect human and base-model baselines.
2. Calibrate thresholds and intervention budgets.
3. Freeze Factorio, FLE, scenario, mod, task, and action-profile versions.
4. Create held-out validation and test seeds/checkpoints.
5. Check verifier invariance across repeated deterministic executions.
6. Red-team reward hacking and privileged-information leakage.
7. Publish failure categories, including lifecycle and terminal-reason metadata.
8. Run every ready microtask repeatedly in randomized order to guard against
   reset leakage.
